# Техническое задание

Проект: Разработка системы аутентификации и авторизации (Identity and Access Management, IAM)

Версия: 1.0

Дата: 27.03.2026

---

## 1. Введение

### 1.1 Общие положения

Настоящий документ определяет требования к разработке и внедрению централизованной системы аутентификации и авторизации (далее — Система), предназначенной для обеспечения безопасного доступа пользователей к веб-приложению и мобильному приложению компании. Документ разработан на основе анализа бизнес-требований, существующей инфраструктуры, лучших практик в области информационной безопасности и требований регуляторов в сфере защиты персональных данных.

### 1.2 Цели и задачи проекта

Основной целью проекта является создание единого, безопасного и удобного механизма управления идентификацией пользователей, который заменит существующие разрозненные решения. Ключевые задачи включают:

*   Обеспечение единого входа (Single Sign-On) для всех цифровых сервисов компании;
*   Внедрение многофакторной аутентификации для снижения рисков компрометации учетных записей;
*   Создание гибкой системы управления правами доступа на основе ролей (RBAC);
*   Обеспечение соответствия требованиям Федерального закона № 152-ФЗ «О персональных данных» и Общего регламента по защите данных (GDPR) для работы с пользователями из Европейского Союза;
*   Обеспечение бесперебойной работы с уровнем доступности не менее 99,95% в годовом исчислении.

### 1.3 Предпосылки создания системы

На момент разработки данного ТЗ существует фрагментированная система аутентификации: веб-приложение использует устаревший механизм на основе сессий PHP, а мобильное приложение — отдельный сервис с собственным хранилищем учетных записей. Отсутствует единый механизм управления сессиями, что создает риски безопасности и негативно влияет на пользовательский опыт (пользователь вынужден авторизовываться отдельно в каждом сервисе). Дополнительным фактором является рост числа попыток несанкционированного доступа (брутфорс-атак), зафиксированных службой информационной безопасности в последние шесть месяцев.

## 2. Назначение

Система предназначена для выполнения следующих функций в интересах трех категорий пользователей:

### 2.1 Конечные пользователи

*   Получение безопасного и удобного доступа к веб-приложению и мобильному приложению с использованием единого логина и пароля;
*   Возможность настройки дополнительных методов защиты (многофакторная аутентификация) по собственному усмотрению;
*   Управление активными сессиями (просмотр устройств, принудительное завершение сеансов на утерянных устройствах);
*   Восстановление доступа при утере пароля или устройства аутентификации.

### 2.2 Администраторы системы

*   Централизованное управление учетными записями пользователей (создание, блокировка, удаление);
*   Назначение и изменение ролей пользователей;
*   Просмотр журналов событий безопасности (логи аутентификации, изменения прав, попытки несанкционированного доступа);
*   Конфигурирование политик безопасности (сложность паролей, срок действия паролей, настройки MFA).

### 2.3 Разработчики и интеграторы

*   Получение унифицированного API для интеграции новых сервисов с единой системой аутентификации;
*   Использование стандартизированных протоколов (OAuth 2.0, OpenID Connect) для подключения сторонних приложений.

## 3. Область применения

Система подлежит внедрению и эксплуатации в следующих средах:

### 3.1 Веб-приложение

Доступ к веб-версии продукта осуществляется через современные браузеры. Система должна корректно функционировать в следующих браузерах:

*   Google Chrome (две последние мажорные версии);
*   Mozilla Firefox (две последние мажорные версии);
*   Apple Safari (две последние мажорные версии) для устройств macOS и iOS;
*   Microsoft Edge (две последние мажорные версии) на базе Chromium.

Особое внимание уделяется корректной работе в режиме инкогнито/приватного просмотра, где возможности хранения данных (localStorage, cookies) могут быть ограничены. В таких случаях система должна использовать альтернативные механизмы хранения токенов или явно информировать пользователя об ограничениях.

### 3.2 Мобильное приложение

Нативные приложения для двух основных мобильных платформ:

*   iOS: версия 15.0 и выше. Поддержка всех актуальных моделей iPhone и iPad. Обязательная поддержка механизмов биометрической аутентификации Face ID и Touch ID через фреймворк LocalAuthentication.
*   Android: API Level 31 (Android 12) и выше. Поддержка различных производителей устройств (Samsung, Xiaomi, Google Pixel и другие). Поддержка биометрической аутентификации через AndroidX Biometric.

### 3.3 API для сторонних интеграций

Система предоставляет программный интерфейс (REST API) для интеграции с внутренними сервисами компании (CRM, биллинг, аналитика) и потенциально — с сервисами партнеров. Доступ к API осуществляется строго через API Gateway с применением rate limiting и валидации токенов.

## 4. Определения и сокращения

| Термин или сокращение | Определение |
| :--- | :--- |
| Аутентификация (AuthN) | Процесс проверки подлинности субъекта доступа (пользователя) путем сравнения предъявленных им идентификаторов и аутентификационных данных с эталонными, хранящимися в системе. |
| Авторизация (AuthZ) | Процесс предоставления субъекту доступа прав на выполнение определенных действий или доступ к ресурсам после успешной аутентификации. |
| MFA (Многофакторная аутентификация) | Метод контроля доступа, требующий предъявления двух и более факторов аутентификации из трех возможных категорий: фактор знания (пароль), фактор владения (устройство, токен), фактор наследования (биометрия). |
| TOTP (Time-based One-Time Password) | Алгоритм генерации одноразовых паролей на основе времени, реализованный в приложениях-аутентификаторах (Google Authenticator, Microsoft Authenticator, Authy). |
| JWT (JSON Web Token) | Открытый стандарт (RFC 7519) для создания компактных, самоописуемых токенов доступа, содержащих утверждения (claims) о пользователе и его правах. |
| Refresh Token | Специальный тип токена, используемый для получения новой пары токенов (access + refresh) без необходимости повторного ввода учетных данных. Имеет длительный срок действия и хранится в защищенном хранилище на клиенте. |
| RBAC (Role-Based Access Control) | Модель управления доступом, в которой права доступа назначаются ролям, а роли — пользователям, что упрощает администрирование прав в крупных системах. |
| IdP (Identity Provider) | Сервис, ответственный за создание, хранение и управление цифровыми идентичностями пользователей, а также за выдачу утверждений об аутентификации другим сервисам. |
| GDPR (General Data Protection Regulation) | Общий регламент Европейского Союза по защите персональных данных, устанавливающий требования к обработке и хранению данных граждан ЕС. |
| OTP (One-Time Password) | Одноразовый пароль, генерируемый системой и отправляемый пользователю по каналам связи (SMS, email) для подтверждения действий или аутентификации. |

## 5. Описание системы

### 5.1 Общая архитектура

Система аутентификации и авторизации строится на принципах микросервисной архитектуры, что обеспечивает горизонтальную масштабируемость, независимость развертывания компонентов и устойчивость к отказам. В состав системы входят следующие компоненты:

1.  Auth Service (Сервис аутентификации): Центральный компонент, отвечающий за проверку учетных данных, генерацию и валидацию токенов, управление сессиями. Реализует бизнес-логику всех операций аутентификации. Написан на языке Go (выбран за высокую производительность при обработке большого количества параллельных запросов и простоту развертывания в виде статически скомпилированного бинарного файла).

2.  User Management Service (Сервис управления пользователями): Отвечает за CRUD-операции с учетными записями, управление ролями, хранение метаданных пользователей (email, телефон, предпочтения). Взаимодействует с Auth Service через внутренний gRPC для минимизации задержек. Использует PostgreSQL в качестве основного хранилища.
3.  Notification Service (Сервис нотификаций): Обеспечивает отправку одноразовых кодов (OTP) через SMS и email, а также push-уведомлений через мобильные приложения. Спроектирован с учетом возможности быстрой замены провайдеров SMS (Twilio, Vonage, локальные агрегаторы) без изменения кода других сервисов.

4.  Session Store (Хранилище сессий): Распределенный кэш на базе Redis Cluster, хранящий активные сессии, refresh токены, информацию о доверенных устройствах и счетчики неудачных попыток входа. Использование кластерной конфигурации Redis исключает единую точку отказа.

5.  API Gateway: Единая точка входа для всех клиентских запросов. Выполняет маршрутизацию, rate limiting, валидацию JWT токенов, проксирование запросов к соответствующим микросервисам. Реализуется на основе Kong или NGINX с Lua-скриптами.

### 5.2 Потоки данных

*   Поток аутентификации (пароль + MFA): Клиент отправляет credentials на API Gateway → Gateway перенаправляет запрос в Auth Service → Auth Service проверяет учетные данные в User Management Service → При успешной проверке пароля проверяет наличие активной MFA-сессии → При необходимости возвращает challenge (требование MFA) → Клиент отправляет MFA-код → Auth Service валидирует код через Notification Service (для SMS/email) или локально (для TOTP) → Генерируется пара токенов (access + refresh), refresh токен сохраняется в Redis → Токены возвращаются клиенту.

*   Поток проверки токена: Клиент отправляет запрос с JWT токеном в заголовке Authorization → API Gateway валидирует подпись токена и срок действия → Gateway проверяет, не находится ли токен в черном списке (Redis) → При успешной проверке запрос передается в целевой сервис с добавленными заголовками (user_id, role).

### 5.3 Обоснование архитектурных решений

Выбор микросервисной архитектуры обусловлен следующими факторами:

*   Масштабируемость: Разные компоненты системы имеют различные профили нагрузки. Auth Service испытывает пиковые нагрузки во время входа пользователей (утренние часы, начало рабочего дня), тогда как User Management Service имеет равномерную нагрузку. Разделение позволяет масштабировать компоненты независимо.
*   Устойчивость: Отказ сервиса нотификаций не должен блокировать возможность входа пользователей с уже установленной доверенной сессией. Изоляция сервисов предотвращает каскадные отказы.
*   Технологическая гибкость: Разные компоненты могут быть реализованы на разных технологических стеках в зависимости от специфики задач.

## 6. Требования к функциональности

### 6.1 Регистрация новой учетной записи

Система должна предоставлять возможность регистрации новых пользователей как через веб-интерфейс, так и через мобильное приложение. Процесс регистрации включает следующие этапы:

*   Ввод адреса электронной почты и номера мобильного телефона (оба поля обязательны для заполнения);
*   Ввод пароля с проверкой на соответствие политике сложности (см. раздел 6.4);
*   Отправка одноразового кода подтверждения на указанный email и SMS (двойное подтверждение для обеспечения актуальности контактных данных);
*   Ввод полученных кодов в интерфейсе регистрации;
*   Создание учетной записи с присвоением роли «Пользователь» по умолчанию.

В случае, если пользователь пытается зарегистрироваться с email или номером телефона, уже существующим в системе, необходимо выводить соответствующее сообщение с предложением восстановить доступ или войти в существующую учетную запись.

### 6.2 Аутентификация с использованием пароля

Базовая аутентификация осуществляется по связке «идентификатор (email или телефон) + пароль». Система должна поддерживать следующие сценарии:

*   Успешный вход с доверенного устройства: При входе с устройства, ранее отмеченного пользователем как доверенное, аутентификация завершается после проверки пароля без запроса MFA.
*   Успешный вход с нового устройства: После успешной проверки пароля система запрашивает прохождение MFA. После успешного прохождения MFA пользователю предлагается добавить устройство в список доверенных.
*   Неудачные попытки: Система ведет счетчик неудачных попыток входа для каждой учетной записи. При достижении 5 неудачных попыток подряд учетная запись блокируется на 15 минут. При достижении 10 неудачных попыток за 24 часа учетная запись блокируется до снятия блокировки администратором (для предотвращения автоматизированных атак подбора паролей).

### 6.3 Многофакторная аутентификация

В связи с высокими рисками компрометации учетных записей (доступ к персональным данным и финансовой информации) MFA является обязательной для всех пользователей, за исключением специальных служебных учетных записей, перечень которых утверждается отдельно.

#### 6.3.1 Доступные методы MFA

Пользователь может выбрать один или несколько методов из перечисленных ниже:

*   TOTP (Time-based One-Time Password): Генерация кодов через приложение-аутентификатор (Google Authenticator, Microsoft Authenticator, Authy). При активации этого метода система отображает QR-код для сканирования и предоставляет секретный ключ для ручного ввода.
*   SMS-код: Отправка 6-значного кода на подтвержденный номер мобильного телефона. Данный метод рассматривается как резервный, так как уязвим для атак перехвата SMS (SIM-swapping). Пользователь должен быть информирован об этом при выборе метода.
*   Push-уведомления: Отправка запроса на подтверждение в мобильное приложение пользователя. Пользователь может подтвердить вход одним касанием или просмотреть детали запроса (устройство, местоположение, время). Данный метод считается наиболее безопасным и удобным.

#### 6.3.2 Бэкап-коды

При первой активации MFA система автоматически генерирует 10 одноразовых бэкап-кодов, каждый длиной 8 символов. Коды отображаются пользователю один раз с рекомендацией сохранить их в надежном месте (не в облачном хранилище, не в скриншотах). Бэкап-коды позволяют восстановить доступ при утере всех устройств аутентификации. После использования кода он удаляется из системы. При использовании 8 из 10 кодов система предлагает сгенерировать новый набор.

#### 6.3.3 Политика применения MFA

*   Вход с нового устройства (определяемого по fingerprint) всегда требует ввода MFA-кода.
*   Изменение чувствительных настроек (смена пароля, изменение email, отключение MFA) требует повторной аутентификации с MFA, даже если сессия активна.
*   Пользователь может настроить период доверия для устройства: 7 дней, 30 дней, 90 дней или «никогда не доверять».

### 6.4 Политика управления паролями

В целях обеспечения безопасности и соответствия требованиям регуляторов, система должна реализовывать следующие правила работы с паролями:

*   Сложность пароля: Минимальная длина 12 символов; обязательное наличие символов из трех из четырех категорий (строчные буквы, прописные буквы, цифры, специальные символы); запрет на использование последовательностей (123456, qwerty) и повторяющихся символов.
*   Хранение паролей: Пароли хранятся исключительно в хэшированном виде с использованием алгоритма bcrypt с фактором стоимости (cost factor) 12, что обеспечивает устойчивость к перебору даже при компрометации базы данных.
*   Срок действия паролей: Пароль действует 90 дней. За 7 дней до истечения срока пользователь получает уведомление с предложением сменить пароль. После истечения срока вход блокируется до смены пароля.
*   Запрет повторного использования: Система хранит хэши последних 5 паролей пользователя и запрещает установку любого из них при смене пароля.

### 6.5 Управление сессиями и устройствами

Пользователь должен иметь возможность просматривать и управлять своими активными сессиями через личный кабинет. Для каждой сессии отображается:

*   Тип устройства (десктоп, мобильный телефон, планшет) на основе User-Agent;
*   Операционная система и браузер (для веб-сессий) или модель устройства (для мобильных приложений);
*   IP-адрес и приблизительное географическое местоположение;
*   Время начала сессии и время последней активности;
*   Индикатор «доверенное устройство».

Пользователь может завершить любую сессию удаленно, после чего соответствующие токены инвалидируются (добавляются в черный список Redis) и клиентские приложения теряют доступ к API.

### 6.6 Восстановление доступа
Процесс восстановления доступа должен быть безопасным и исключать возможность несанкционированного захвата учетной записи:

*   Пользователь на странице входа выбирает «Забыли пароль?»;
*   Указывает email или номер телефона, связанный с учетной записью;
*   Система отправляет одноразовый код подтверждения (6 цифр) на оба канала связи (email и SMS);
*   Пользователь вводит полученный код;
*   После успешной проверки кода пользователь может установить новый пароль (с соблюдением политики сложности);
*   При смене пароля все активные сессии пользователя инвалидируются, за исключением текущей сессии, в которой производится смена пароля;
*   Пользователь получает уведомление об изменении пароля на все зарегистрированные каналы связи.

### 6.7 Ролевая модель доступа (RBAC)

Система реализует три базовые роли с возможностью расширения в будущем:

| Роль | Описание | Примеры прав |
| :--- | :--- | :--- |
| Пользователь | Базовая роль для всех авторизованных пользователей | Доступ к личному кабинету, изменение своих данных, просмотр своей истории входов |
| Администратор | Управление системой и пользователями | Создание/блокировка учетных записей, просмотр логов всех пользователей, изменение политик безопасности |
| Аудитор | Только чтение логов и отчетов (разделение обязанностей) | Просмотр журналов аутентификации, экспорт отчетов без права внесения изменений |

### 6.8 Интеграция с внешними сервисами (Social Login)

Для повышения удобства пользователей и снижения барьера входа система поддерживает аутентификацию через внешних провайдеров:

*   Google OAuth 2.0: Вход через учетную запись Google;
*   Apple ID: Обязательная поддержка для соответствия требованиям App Store Review Guidelines (приложения, использующие сторонние системы входа, обязаны предоставлять вход через Apple ID).

При первом использовании социального входа система создает новую учетную запись (если пользователь не найден по email) или связывает внешний идентификатор с существующей учетной записью (после дополнительного подтверждения). MFA для таких пользователей остается обязательной — после аутентификации через внешнего провайдера может потребоваться дополнительный MFA-фактор.

## 7. Технические условия

### 7.1 Требования к серверной инфраструктуре

#### 7.1.1 Минимальные аппаратные требования

Система должна функционировать на следующем минимальном оборудовании (из расчета на среднюю нагрузку до 50 000 активных пользователей):

| Компонент | CPU | RAM | Storage | Примечания |
| :--- | :--- | :--- | :--- | :--- |
| Auth Service (3 узла) | 2 vCPU | 4 GB | 20 GB SSD | Горизонтальное масштабирование через балансировщик |
| User Management Service (2 узла) | 2 vCPU | 4 GB | 20 GB SSD | |
| Notification Service (2 узла) | 1 vCPU | 2 GB | 10 GB SSD | |
| PostgreSQL (кластер) | 4 vCPU | 16 GB | 100 GB SSD (NVMe) | Master + replica, WAL archiving |
| Redis Cluster (3 master + 3 replica) | 2 vCPU | 8 GB | 50 GB SSD (NVMe) | Выделенные узлы для снижения задержек |
| API Gateway (2 узла) | 2 vCPU | 4 GB | 20 GB SSD | |

Обоснование: Выбор 4 vCPU для PostgreSQL обусловлен необходимостью обработки сложных запросов на JOIN при управлении ролями и правами. Выделенные 16 ГБ RAM для PostgreSQL позволяют эффективно кэшировать часто запрашиваемые данные (user profiles) в shared_buffers, снижая нагрузку на диск.

#### 7.1.2 Требования к программному обеспечению

*   Операционная система: Ubuntu 22.04 LTS (поддержка до апреля 2027 года) или Rocky Linux 9 (для организаций, предпочитающих Red Hat-совместимые дистрибутивы).
*   СУБД: PostgreSQL 15 или выше с расширением pgcrypto для хэширования.
*   Кэш: Redis 7.0 или выше в кластерной конфигурации.
*   Оркестрация: Kubernetes 1.27+ (для production-окружения) с возможностью отката версий и автоматического восстановления при сбоях узлов.
