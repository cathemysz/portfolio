# Введение

Данный документ описывает декомпозицию требований к сервису аутентификации и авторизации. Цель — перевести технические и бизнес-требования в практичные, ориентированные на пользователя сценарии (User Stories) и детализированные варианты использования (Use Cases). Это позволяет команде разработки понимать не только что нужно реализовать, но и зачем, с учётом аспектов безопасности, масштабируемости, удобства использования и соответствия нормативным требованиям.

---

# Раздел Use Case (Варианты использования)

На основе описанных User Stories представлены 5 вариантов использования с детальной структурой.

---

## Use Case №1: Аутентификация пользователя с паролем и 2FA

*   Название: Аутентификация пользователя с использованием пароля и двухфакторной аутентификации.
*   Описание: Пользователь вводит свои учётные данные (логин/пароль) и подтверждает вход с помощью одноразового кода из приложения-аутентификатора.
*   Акторы: Конечный пользователь.
*   Предусловия:
    *   Пользователь зарегистрирован в системе.
    *   У пользователя включена двухфакторная аутентификация.
    *   Сервис аутентификации доступен.
*   Постусловия:
    *   Успешное: Пользователь получает access и refresh токены. Сессия зарегистрирована в системе. Событие успешного входа залогировано.
    *   Неуспешное: Пользователь остаётся неаутентифицированным. Попытки входа фиксируются для защиты от brute-force.
*   Основной поток (Success Path):
    1.  Пользователь открывает страницу входа.
    2.  Пользователь вводит email и пароль.
    3.  Система проверяет учётные данные и статус пользователя (не заблокирован, активен).
    4.  Система запрашивает код двухфакторной аутентификации.
    5.  Пользователь вводит корректный TOTP-код из приложения-аутентификатора.
    6.  Система проверяет код, генерирует JWT-токены и создаёт запись об активной сессии.
    7.  Система перенаправляет пользователя в защищённую область приложения.
*   Альтернативные потоки:
    *   3a. Неверный пароль: Система отображает сообщение об ошибке. Счётчик неудачных попыток увеличивается. При превышении лимита учётная запись временно блокируется.
    *   5a. Неверный 2FA код: Система отображает сообщение об ошибке и предлагает повторить ввод.
    *   5b. Пользователь потерял доступ к 2FA: Пользователь использует резервные коды восстановления (альтернативный поток для восстановления доступа).

## Use Case №2: Управление ролями и правами доступа

*   Название: Управление ролями и разграничение доступа.
*   Описание: Администратор создаёт новую роль и назначает ей набор прав (permissions), а затем назначает эту роль пользователям для контроля доступа к ресурсам.
*   Акторы: Системный администратор.
*   Предусловия:
    *   Администратор аутентифицирован в системе.
    *   Учётная запись администратора имеет привилегию «Управление ролями».
*   Постусловия:
    *   Создана новая роль с определённым набором прав.
    *   Изменения в системе прав доступа зафиксированы в аудит-логе.
    *   Пользователи, получившие новую роль, теперь имеют доступ к соответствующим ресурсам.
*   Основной поток:
    1.  Администратор открывает раздел «Управление ролями».
    2.  Система отображает список существующих ролей.
    3.  Администратор нажимает «Создать роль» и вводит название (например, «Контент-менеджер»).
    4.  Система предлагает список доступных прав (permissions): «Редактировать статьи», «Публиковать новости», «Удалять комментарии».
    5.  Администратор выбирает нужные права и сохраняет роль.
    6.  Администратор переходит в раздел «Пользователи», выбирает пользователя и назначает ему новую роль.
    7.  Система сохраняет назначение и логирует действие.
*   Альтернативные потоки:
    *   3a. Удаление роли: Если роль назначена пользователям, система предупреждает об этом и требует подтверждения перед удалением.
    *   6a. Изменение прав существующей роли: При изменении прав роли система применяет новые правила доступа для всех пользователей, имеющих эту роль, без необходимости их переназначения.

## Use Case №3: Завершение подозрительной сессии

*   Название: Управление активными сессиями пользователя.
*   Описание: Пользователь обнаруживает в списке активных сессий неизвестное устройство и принудительно завершает эту сессию для предотвращения несанкционированного доступа.
*   *   Акторы: Конечный пользователь.
*   Предусловия:
    *   Пользователь аутентифицирован в системе (например, на своём основном устройстве).
    *   В системе зарегистрировано несколько активных сессий пользователя (телефон, браузер, другое устройство).
*   Постусловия:
    *   Указанная сессия аннулирована.
    *   Токены доступа (access/refresh) для этой сессии становятся недействительными.
    *   Пользователь на удалённом устройстве автоматически выходит из системы (или получает ошибку 401 при следующем запросе).
    *   Событие завершения сессии зафиксировано в аудит-логе.
*   Основной поток:
    1.  Пользователь заходит в настройки профиля и выбирает раздел «Активные сессии».
    2.  Система отображает список устройств, местоположений (по IP) и времени последней активности.
    3.  Пользователь видит подозрительную сессию (например, «Chrome на Windows, Москва, 5 минут назад») и нажимает кнопку «Завершить сессию».
    4.  Система запрашивает подтверждение действия (защита от случайного нажатия).
    5.  Пользователь подтверждает.
    6.  Система аннулирует токены этой сессии и удаляет её из списка активных.
    7.  Пользователь видит сообщение об успешном завершении.
*   Альтернативные потоки:
    *   1a. Обработка уведомления: Пользователь получает push-уведомление или email «Новый вход с устройства...» и нажимает в уведомлении кнопку «Завершить эту сессию» (без необходимости входа в профиль, но с повторной краткой аутентификацией для подтверждения личности).

## Use Case №4: Интеграция внешнего приложения через OAuth 2.0

*   Название: Авторизация стороннего приложения (OAuth 2.0 / OpenID Connect).
*   Описание: Внешнее приложение (клиент) запрашивает доступ к данным пользователя. Пользователь проходит аутентификацию и даёт согласие на предоставление прав.
*   Акторы: Конечный пользователь, Внешнее приложение (клиент).
*   Предусловия:
    *   Внешнее приложение зарегистрировано в сервисе аутентификации (имеет client_id и client_secret).
    *   Пользователь не аутентифицирован в текущей сессии браузера (или сессия есть, но требуется подтверждение доступа).
*   Постусловия:
    *   Внешнее приложение получает authorization code, а затем access token (и id token, если используется OIDC).
    *   Пользователь получает доступ к функциям внешнего приложения без передачи ему своих учётных данных.
*   Основной поток:
    1.  Пользователь переходит во внешнее приложение и нажимает «Войти через систему X».
    2.  Внешнее приложение перенаправляет пользователя на сервер аутентификации (наш сервис) с запросом авторизации.
    3.  Сервис аутентификации проверяет наличие активной сессии пользователя. Так как сессии нет, отображается форма входа.
    4.  Пользователь вводит логин и пароль (проходит 2FA, если настроено).
    5.  Сервис отображает экран согласия: «Приложение Запросник запрашивает доступ к вашему профилю и email. Разрешить?».
    6.  Пользователь нажимает «Разрешить».
    7.  Сервис перенаправляет пользователя обратно во внешнее приложение с временным кодом (authorization code).
    8.  Внешнее приложение обменивает код на токены (access token, refresh token) через backend-канал (client_secret).
*   Альтернативные потоки:
    *   3a. Уже есть сессия: Если пользователь уже вошёл в сервис аутентификации в том же браузере, шаги 3-4 пропускаются, система сразу переходит к экрану согласия.
    *   6a. Отказ в доступе: Пользователь нажимает «Запретить». Сервис перенаправляет пользователя обратно во внешнее приложение с сообщением об ошибке (access_denied). Приложение не получает код.

## Use Case №5: Аудит событий безопасности

*   Название: Просмотр и экспорт логов аутентификации и авторизации.
*   Описание: Аудитор безопасности запрашивает журнал событий за определённый период для анализа инцидента или плановой проверки соответствия стандартам.
*   Акторы: Аудитор безопасности.
*   Предусловия:
    *   Аудитор аутентифицирован в системе.
    *   Учётная запись аудитора имеет роль с правом «Просмотр аудит-логов».
    *   В системе настроено централизованное хранение логов с гарантией неизменяемости.
*   Постусловия:
    *   Аудитор получает структурированный отчёт (CSV/JSON) с событиями.
    *   Сам факт выгрузки логов также фиксируется в системе аудита для отслеживания действий самого аудитора.
*   Основной поток:
    1.  Аудитор открывает интерфейс управления безопасностью и переходит в раздел «Аудит событий».
    2.  Система отображает фильтры: диапазон дат, тип события (вход, выход, смена пароля, изменение роли, отказ в доступе), идентификатор пользователя.
    3.  Аудитор задаёт параметры (например: «все неудачные попытки входа за последние 7 дней») и нажимает «Применить».
    4.  Система выполняет запрос к хранилищу логов (с учётом высокой нагрузки и масштабируемости) и отображает результаты постранично.
    5.  Аудитор нажимает «Экспортировать».
    6.  Система генерирует файл с данными и сохраняет факт экспорта в отдельный лог аудита.
*   Альтернативные потоки:
    *   4a. Объём данных слишком велик: Система предлагает настроить фильтры для уменьшения выборки или запланировать фоновую выгрузку с уведомлением по email (для сохранения производительности сервиса).

# Заключение

В ходе выполнения задания были декомпозированы исходные требования к сервису аутентификации и авторизации. На их основе сформулированы 10 пользовательских историй, которые охватывают потребности различных категорий пользователей: от конечных пользователей, заботящихся о безопасности и удобстве, до администраторов и аудиторов, отвечающих за управление доступом и соответствие стандартам.

На основе этих историй разработаны 5 детализированных вариантов использования (Use Cases), описывающих ключевые сценарии:

1.  Основной процесс входа с усиленной защитой (2FA).
2.  Гибкое управление доступом на основе ролей (RBAC).
3.  Контроль пользователем своих активных сессий для повышения безопасности.
4.  Интеграция со сторонними приложениями по стандарту OAuth 2.0.
5.  Обеспечение прозрачности и соответствия требованиям через механизм аудита.

Такой подход позволяет увязать абстрактные технические требования (масштабируемость, безопасность, соответствие стандартам) с конкретными действиями пользователей и функциями системы, что является основой для качественной разработки и последующего тестирования.
